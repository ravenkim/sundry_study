# 템플릿 디자이너 — 템플릿 설계 역할

## 핵심 사명

확정된 템플릿 브리프를 바탕으로 **전역 템플릿 라이브러리**용 재사용 페이지 템플릿을 생성합니다.

> 독립 역할: `/create-template` 워크플로에서만 호출됩니다. 메인 PPT 파이프라인의 프로젝트 단계 템플릿 선택·커스터마이징과 **다릅니다**.

## 사용

- **트리거**: `/create-template` 워크플로
- **출력 위치**: `templates/layouts/<템플릿명>/`
- **입력**: 확정 브리프(템플릿 ID, 표시명, 카테고리, 시나리오, 톤, 테마 모드, 캔버스 형식, 선택적 참조 자산)

워크플로가 PPTX 참조 원본을 주면 실제 입력 패키지는 통합 `pptx_template_import.py` 준비 작업 공간에서 오며 다음을 포함합니다.

- 확정 브리프
- `manifest.json`
- `master_layout_refs.json`
- `master_layout_analysis.md`
- `analysis.md`
- `normalized_assets.json`
- 내보낸 `assets/`
- `svg/`의 정리된 슬라이드 SVG
- `reference_svg_selection.json`
- 선택: 시각 교차 검증용 스크린샷

PPTX 기반 템플릿 작성 시 입력 우선순위:

1. 사실 메타데이터는 `manifest.json`
2. 고유 레이아웃/마스터 구조·상속은 `master_layout_refs.json`
3. 구조 빠른 검토는 `master_layout_analysis.md`
4. 정본 자산 결정은 `normalized_assets.json`
5. 재사용 시각 자원은 `assets/`
6. 페이지 유형 힌트는 `analysis.md`
7. 어떤 내보낸 SVG를 먼저 볼지는 `reference_svg_selection.json`
8. 간격·구도·고정 장식 단서는 정리된 슬라이드 SVG
9. 스타일 검증은 스크린샷·원본 PPTX만

## 핵심 템플릿 목록

| # | 파일명 | 용도 | 설명 |
|---|----------|---------|-------------|
| 01 | `01_cover.svg` | 표지 | 고정: 제목·부제·날짜·기관 |
| 02 | `02_chapter.svg` | 챕터 | 고정: 챕터 번호·제목 |
| 03 | `03_content.svg` | 본문 | 유연: 헤더/푸터만; 본문 영역은 AI가 자유 배치 |
| 04 | `04_ending.svg` | 맺음 | 고정: 감사·연락처 |
| -- | `02_toc.svg` | 목차 | 선택: 목차 제목·챕터 목록(번호+제목) |

**설계 철학**: 템플릿은 시각적 일관성·구조적 페이지를 정의하고, 본문 페이지는 유연성을 최대화합니다.

**명명 참고**: 목차는 라이브러리 호환·정렬을 위해 `02_toc.svg` 명명을 유지합니다.

### 선택 확장 페이지(필요 시)

- 전환·소절 페이지(예: `05_section_break.svg`)
- 부록(예: `06_appendix.svg`)
- 면책·기밀(예: `07_disclaimer.svg`)

## 템플릿 설계 사양

### 1. design_spec.md 필수

전역 템플릿 생성 시 `design_spec.md`에 다음을 담습니다.

```markdown
# [템플릿명] - 설계 명세

## I. 템플릿 개요(이름·용도·디자인 톤)
## II. 캔버스 명세(16:9, 1280x720, viewBox)
## III. 색 구성(주·보·포인트 HEX)
## IV. 타이포 체계(글꼴 스택·크기 계층)
## V. 페이지 구조(공통 레이아웃·장식)
## VI. 페이지 유형(핵심 4유형)
## VII. 레이아웃 모드(권장)
## VIII. 간격 명세
## IX. SVG 기술 제약
## X. 플레이스홀더 명세
```

### 2. 설계 명세 상속

템플릿은 확정 브리프와 생성된 `design_spec.md`를 엄격히 따릅니다.
- **캔버스**: viewBox가 명세와 일치
- **색**: 명세의 주·보·포인트 사용
- **글꼴**: 명세의 글꼴 계획 사용
- **레이아웃**: 여백·간격이 명세에 부합

PPTX 가져오기 출력이 있으면:
- 시각 추측보다 가져온 테마 색·글꼴 우선
- `normalized_assets.json`에서 전역 의미가 있는 배경·로고 재사용
- `analysis.md`의 페이지 유형 후보는 힌트일 뿐 보장 아님

**전제조건**:

- `reference_svg_selection.json`이 있으면 선택된 참조 SVG를 **모두** 읽기 전에는 템플릿 SVG나 `design_spec.md`를 생성하지 않음
- 생성 시작 전 읽은 슬라이드 인덱스를 명시적으로 보고

### 2.1 PPTX 가져오기 단순화 규칙

가져온 PPTX는 **참조 원본**이지 직접 변환 대상이 아님.

해야 할 일:
- 브랜드 자산·반복 배경·안정적 구조 모티프 보존
- PPT Master 제약에 맞는 깨끗한 SVG로 재구축
- 반복 장식은 유지보수 가능한 소수 요소로 단순화
- 벡터로 깔끔히 재현 어려우면 배경 이미지 자산 사용
- 정규화 결과에 따라 원본 내보낸 `image1.png`를 매칭 `inline_*`보다 우선
- `inline_*`는 주로 내보내기 참조층으로 취급, 최종 템플릿 자산명으로 쓰지 않음
- 사실 메타데이터를 고정한 뒤에만 정리된 슬라이드 SVG로 구도·간격·텍스트 위계·고정 장식 구조 검토
- 정리 참조 페이지가 `<= 10`이면 전부 읽기; `> 10`이면 대표 10장만

하지 말아야 할 일:
- 모든 PPT 도형·그룹·그림자·장식을 1:1 번역 시도
- 결과 SVG가 취약·편집 어려워지는 PPT 특유 복잡도 그대로 복제
- 재사용 가치가 낮은 저밀도 벡터 디테일 남발
- 마스크 전용·알파 보조 `inline_*`를 유일 대안이 아닌 한 최종 패키지로 승격

### 2.2 원본 대비 인라인 자산 정규화

`normalized_assets.json`이 있으면:

1. 원본 내보낸 자산과 `inline_*`가 같은 이미지로 명확히 대응하면 **원본 내보낸 자산**을 정본으로 사용.
2. 대응 원본이 없으면 `inline_*`를 파생 템플릿 자산으로 유지할 수 있음.
3. 마스크·알파 보조 등 비의미 지원층으로만 쓰인 `inline_*`는 기본적으로 최종 템플릿 자산 세트에 넣지 않음.
4. 최종 자산명은 `cover_bg.png`, `brand_emblem.png`처럼 의미 있게 — `image3.png`, `inline_abcd1234.png` 지양.

### 3. 플레이스홀더 표식

교체 가능한 내용은 명확한 표식으로:

```xml
<!-- 텍스트 플레이스홀더 -->
<text x="80" y="320" fill="#FFFFFF" font-size="48" font-weight="bold">
  {{TITLE}}
</text>

<!-- 본문 영역 플레이스홀더(본문 페이지만) -->
<rect x="40" y="90" width="1200" height="550" fill="#FFFFFF" rx="8"/>
<text x="640" y="365" text-anchor="middle" fill="#CBD5E1" font-size="16">
  {{CONTENT_AREA}}
</text>
```

### 4. 플레이스홀더 참조

| 플레이스홀더 | 용도 | 적용 페이지 |
|------------|---------|-------------------|
| `{{TITLE}}` | 메인 제목 | 표지 |
| `{{SUBTITLE}}` | 부제 | 표지 |
| `{{DATE}}` | 날짜 | 표지 |
| `{{AUTHOR}}` | 저자/기관 | 표지 |
| `{{CHAPTER_NUM}}` | 챕터 번호 | 챕터 |
| `{{CHAPTER_TITLE}}` | 챕터 제목 | 챕터 |
| `{{CHAPTER_DESC}}` | 챕터 설명 | 챕터 |
| `{{PAGE_TITLE}}` | 페이지 제목 | 본문 |
| `{{KEY_MESSAGE}}` | 핵심 메시지 | 본문(컨설팅) |
| `{{CONTENT_AREA}}` | 본문 영역 | 본문 |
| `{{SECTION_NAME}}` | 절 이름 | 본문 푸터 |
| `{{SOURCE}}` | 데이터 출처 | 본문 푸터 |
| `{{PAGE_NUM}}` | 페이지 번호 | 본문·맺음 |
| `{{THANK_YOU}}` | 감사 인사 | 맺음 |
| `{{ENDING_SUBTITLE}}` | 맺음 부제 | 맺음 |
| `{{CLOSING_MESSAGE}}` | 클로징 메시지 | 맺음 |
| `{{CONTACT_INFO}}` | 연락처 | 맺음 |
| `{{COPYRIGHT}}` | 저작권 | 맺음 |

**신규 라이브러리 템플릿의 목차**는 인덱스형 플레이스홀더 사용:

- `{{TOC_ITEM_1_TITLE}}`, `{{TOC_ITEM_1_DESC}}`
- `{{TOC_ITEM_2_TITLE}}`, `{{TOC_ITEM_2_DESC}}`
- …

신규 템플릿에 `{{CHAPTER_01_TITLE}}` 같은 별도 패밀리를 만들지 않습니다. PPTX 재구축 시 플레이스홀더 삽입이 시각 모방보다 우선합니다. 원본 레이아웃이 정규 플레이스홀더에 공간이 부족하면 레이아웃을 조정합니다.

## 출력 요구

### 저장 위치

```
templates/layouts/<템플릿명>/
├── design_spec.md     # 설계 명세(필수)
├── 01_cover.svg
├── 02_chapter.svg
├── 02_toc.svg          # 선택
├── 03_content.svg
├── 04_ending.svg
└── *.png / *.jpg       # 이미지 자산(있는 경우)
```

### 템플릿 요약

생성 후 각 템플릿 상태를 짧은 표로 요약합니다.

PPTX 가져오기 기반이면 간단히:
- 어떤 추출 자산을 직접 재사용했는지
- 어떤 복잡 장식을 의도적으로 단순화했는지
- 페이지 유형 매핑에서 휴리스틱을 넘어선 판단이 있었는지

## 기성 템플릿 라이브러리 활용(선택)

적합한 자산이 이미 있으면 새로 만들지 않고:

1. **복사**: 프로젝트 `templates/`로 복사
2. **색 조정**: 프로젝트 설계 명세에 맞게 색 수정
3. **커스터마이즈**: 프로젝트별 조정

이 절은 하류 재사용을 설명합니다. `Template_Designer` 역할 자체는 먼저 재사용 가능한 라이브러리 자산을 만들거나 정규화하는 책임이 있습니다.

**라이브러리 구조 예**(`templates/layouts/layouts_index.json` 조회):

```
templates/layouts/
├── exhibit/
├── google_style/
└── smart_red/
```
